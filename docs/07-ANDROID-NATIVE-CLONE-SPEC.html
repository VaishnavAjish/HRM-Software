01 — Scope

What you keep, what you rebuild

The system today is a Laravel API with a React single-page frontend wrapped in Capacitor for mobile. The database and every business rule live server-side. That means a native Android client is a presentation-layer replacement only — you are not porting logic, you are re-implementing screens against an API that already exists and already enforces its own access rules.

LayerTodayIn the Android build
DatabaseMySQL · 24 tablesUntouched
Business logicLaravel controllersUntouched
Authtymon/jwt-authUntouched — consume the same JWT
Access controlRoleMiddleware + RBAC tablesUntouched — mirror it in the UI only
ClientReact 18 + TailwindRebuild — Kotlin + Compose
Mobile shellCapacitor WebViewDrop entirely
Camera@capacitor/camera + getUserMediaRebuild — CameraX
PDF / payslipsClient-side jsPDFRebuild — see §09
Excel importClient parses, posts rowsOptional — admin-desktop task
Key consequence

Because the API enforces role and tenancy server-side, UI permission checks in the Android app are a convenience, never a security boundary. An employee calling the salary-slip endpoint is already forced to their own emp_code in SalariesSlipController::index. Build the UI gates for usability and let the server be the authority.

Three apps or one?

The web app is a single build that branches on role at login. For Android you have a real choice. One app with a role-switched navigation graph shares ~70% of its code (auth, networking, profile, theming) and is a single Play listing. Three separate apps give each audience a smaller download and a purpose-built launcher, at the cost of maintaining three shells.

Recommendation: one app, three navigation graphs. The employee and agent surfaces are small (5 and 3 screens); splitting them out buys little and triples release work. Use a single :app module with per-role feature modules so you can split later without rewriting.

02 — Authentication

Auth & session model

Login

One endpoint, and the identifier field is deliberately loose: the parameter is named email but the server decides what it actually is. 

POST /api/login
{ "email": "<email OR emp_code>", "password": "...", "company_code": "nidhi-impex,silver-star" }

// Server picks the column by inspecting the value:
// filter_var($input, FILTER_VALIDATE_EMAIL) ? 'email' : 'emp_code'

// 200 →
{ "status": true, "message": "Login successful",
  "token": "<JWT>", "token_type": "Bearer", "user": { ...full user row... } }

Your login field must therefore accept both and never validate as email-only. All subsequent calls send Authorization: Bearer <token>.

Login-time side effects to replicate

  • is_deleted == 1 → 403 "Account is deactivated".
  • status == 2 (pending) → silently flipped to 0 on first successful login.
  • Wrong credentials → 401 "Invalid credentials".

No refresh flow

There is no token-refresh endpoint. Whatever TTL the server is configured with is a hard session ceiling, and the user is bounced to login when it lapses. If long-lived sessions matter on mobile, that is a backend change — plan for it explicitly rather than discovering it in testing.

Forgot password — four steps, one endpoint

This is the most unusual route in the system. Laravel registers POST /api/new{data} as a wildcard, so /new-email, /new-email-otp, /new-password and /new-emp_code all hit the same handler. The URL suffix is cosmetic — dispatch happens on a type field in the body. Rate limited to 15 requests/minute.

typePurposeBodyEffect
0Verify identityemp_code, mobile_number, company_code, unit, photo?Cross-checks mobile on file; issues 15-min verification_token. Rate-limited 5/code/hr, 20/IP/hr
1Send OTPemailEmails a 4-digit OTP, stores it on users.otp
2Verify OTPemail, otpCompares to stored value. Does not consume it
3Set passwordemail, passwordWrites new password, clears otp, status 2→0

The live web UI only uses types 1 → 2 → 3 (email + OTP + new password). Type 0 exists for an emp-code identity path the current UI no longer calls. Password rule enforced client-side: 6+ chars with upper, lower, digit and special character.

Security defect — do not copy

Step 3 only checks that users.otp is non-null; it never re-verifies the submitted OTP, and step 2 doesn't consume or flag anything on success. Anyone who knows a target's email can call type 1 then type 3 and reset that password without ever seeing the OTP. The OTP also never expires and is stored in plaintext. Fix this server-side before shipping a new client onto it — see §11.

03 — Access control

Roles & permissions

Access is decided by two columns on users that must be read together: an integer role and a string type.

roleMeaningData scopeResolves to
0Super AdminEverything, all companiesadmin
1AdminOwn company_code onlyadmin
2Unit AdminOwn company_code + unitadmin
3EmployeeOwn records onlyemployee
4AgentCandidates they createdagent

Resolution algorithm — mirror this exactly

// RoleMiddleware.php (server) and AuthContext.jsx (client) must agree
fun resolveRole(user: User): Role = when {
    user.type == "agent" || user.role == 4        -> Role.AGENT
    user.role in setOf(0, 1, 2)                   -> Role.ADMIN
    else                                          -> Role.EMPLOYEE
}

Note the ordering: agent is tested first. A row with type = "agent" is an agent regardless of its integer role. Getting this order wrong sends agents into the admin graph.

Per-user page permissions (RBAC)

On top of the coarse role, super admins can grant or revoke individual pages per user. The implementation is unusual: rather than shared named roles, each user gets a private role row named User_{id}_Permissions, and page grants are stored as permission_dimensions rows with dimension = 'page'. 

GET /api/my-permissions          // any authenticated user

// → { "status": true, "data": [ { "key_name": "salary", "value": "read_write" }, ... ] }

// value ∈ { "no_access" | "view_only" | "read_write" }
// role 0 (Super Admin) bypasses entirely — treat permissions as null = allow all
// missing key → default ALLOW (the model is permissive, not deny-by-default)

Permissive by default

A key absent from the response means allowed, not denied — the web client does permissions[key] !== "no_access". Replicate that polarity or you will hide navigation from everyone the moment RBAC rows are missing.

04 — Multi-tenancy

Company & unit scoping

Nearly every list endpoint is filtered by a two-level tenant key. Getting this wrong is the most likely source of "why is this list empty" during your build.

Companycompany_codeUnitsTheme
Nidhi Impexnidhi-impexShreeji, IchapurAmber
Silver Star Diam Pvt Ltdsilver-starDaduk, IchapurSky blue

Rules that bite

  • all-companies is a client-side pseudo-scope only. The server has never heard of it. The web client expands it into a comma-joined list (company_code=nidhi-impex,silver-star) before sending. You must do the same.
  • Only role 0 may pick a company. Roles 1 and 2 have their scope forced from their own user row server-side, so sending a different company_code is ignored.
  • Writes take a single company code, never a list. Reads accept a comma list.
  • Ichapur belongs to both companies. Unit alone never identifies a tenant — always pair it with company_code.
  • The server normalizes loosely (nidhi, nidhiimpex, nidhi_impex all resolve). Don't rely on it; send the canonical slug.

In Compose, model this as a single app-level CompanyScope(companyId, unit) exposed from a repository, and have every list request read from it. The web app keeps it in a React context; the equivalent is one StateFlow that survives navigation.

05 — Domain model

How a person becomes an employee

This is the core domain concept and the part most likely to be misunderstood. Candidates, appointments, agents and employees are all rows in the same users table, distinguished by type and status. There is no separate candidates table.

The filters each list applies

// Employees list — GET /api/employee/get
is_deleted = 0 AND role NOT IN (0,1,2)
  AND emp_code IS NOT NULL AND emp_code != ''
  AND (type IS NULL OR type NOT IN ('appointment','agent','pending_employee'))

// Pending list — GET /api/employee/get?status=2

// Appointments — GET /api/appointment

  OR (type IS NULL/'' AND emp_code IS NULL/'')   // legacy untyped rows
Default password

A newly submitted appointment is created with the hard-coded password 12345678 and role = 3. Assigning an emp code does not change it; only the Pending-Employees password step does. Every employee onboarded through this flow therefore shares one known password until an admin sets a real one. Treat the password step as mandatory, not optional, in your UI.

Non-REST conventions

Several destructive operations use GET (/employee/delete/{id}, /admin/salary-slip/delete?id=) and several updates use POST where PUT would be expected. Don't "correct" these in your Retrofit interface — match the server exactly or the calls 405.

Three things that need real design work

1 · The envelope

Every response wraps its payload and can report failure with HTTP 200. Centralize this once in an interceptor or a Result mapper rather than checking status at 78 call sites. Also note the payload key is inconsistent across endpoints — data, user, login, employee all appear. The web client coalesces with data?.login || data?.data || data?.user || data; your deserializer needs the same tolerance.

2 · Payslip and Form 16 rendering

These are currently generated client-side from raw slip rows — the layout lives in React components, not on the server. You have three options, in increasing order of effort: request a server-side PDF endpoint (cleanest, needs backend work); rebuild the layout in Compose and print via PdfDocument; or render an HTML template in a headless WebView and print that. If you want zero backend change, the third reuses the existing markup most directly.

3 · Attendance grid

The response is { employees[], attendance: { emp_code: { "YYYY-MM-DD": status } }, days_in_month } — a sparse nested map, not a list. A month × headcount grid is wide; on a phone prefer a per-employee calendar (which the web app already falls back to) over a scrollable matrix. Cell edits are single upserts, and sending an empty status deletes the record rather than storing a blank.

Free wins from going native

Camera works without HTTPS (the WebView build cannot use getUserMedia over a plain LAN address); real file pickers; biometric unlock over the stored JWT; push notifications for payslip-published events; genuine offline reads. None of these need backend changes except push.

10 — Sequencing

Delivery phases

Ordered so each phase ships something usable and each one de-risks the next. Phase 1 exists because auth, tenancy and the response envelope are shared by everything — get them wrong and every later phase inherits the mistake.

  1. 1

    Foundation

    Login accepting email or emp code, secure token storage, session restore via /profile, 401 → logout, role resolution, company scope holder, envelope handling, design system.

    Ships: nothing user-facing · Unblocks: everything

  2. 2

    Employee app — the MVP

    Dashboard, payslip list and detail, profile with the 19-field completeness gate, change password, forgot password. Smallest surface, largest audience, and it exercises the whole foundation.

    5 screens · 6 endpoints · Ships to the most users

  3. 3

    Agent app

    Candidate list, trial form, and the full appointment form with CameraX photo and document capture. This is where native pays for itself.

    3 screens · 7 endpoints · Validates camera + long forms

  4. 4

    Admin core

    Dashboard, employee list and detail, appointments with emp-code assignment, pending employees with password assignment. The daily-driver admin loop, excluding bulk work.

    Covers the full onboarding pipeline end to end

  5. 5

    Admin operations

    Attendance marking, shifts, salary browsing, payslip PDF export. Attendance is a phone-first task and deserves a purpose-built UI, not a ported grid.

    Needs the PDF decision from §09 resolved

  6. 6

    Long tail

    RBAC administration, audit trail, TDS, Form 16, reports, bulk spreadsheet upload. Reasonable to leave on the web admin permanently — these are desk tasks, not phone tasks.

    Deliberately last · consider never

Minimum viable clone

If you want the shortest path to something genuinely usable: phases 1 + 2. That is one login screen, four employee screens, six endpoints, and it serves the largest group of users in the system. Everything else is additive.

11 — Warnings

Traps & known defects

Found while reading the source. The first three are security issues in the existing backend that a new client will inherit — worth fixing before you point a second app at them.

Defect · password reset bypasses OTP

setNewPasswordAfterVerification checks only that users.otp is non-null, and OTP verification never marks or consumes it. Knowing a target's email is enough to reset their password. Fix: require the OTP again on the final step, or mark it verified and consumed. The OTP is also stored in plaintext with no expiry.

Defect · shared default password

Every appointment-created row gets 12345678. Because login accepts emp_code and codes are guessable, anyone can sign in as an employee who hasn't changed it. There is no forced change on first login. Consider a per-user random password surfaced to the admin, plus a must-change flag.

Defect · unauthenticated appointment endpoints

POST /appointment, GET /appointment and /appointment/check-emp-code require no token. The write path is guarded by an allow-list so role and password can't be injected, but GET /appointment exposes candidate PII — names, mobiles, Aadhaar and bank fields — to anyone. Authenticate the read before shipping.

Hard deletes

The User model has no SoftDeletes trait, so /employee/delete/{id} permanently removes the row. An is_deleted column exists and is used for deactivation, but the delete endpoint does not use it. Confirm destructively in your UI and say so plainly.

Duplicated columns in salary_slips

total_deduct vs total_deduction, net_payable vs net_salary, gross_salary vs a_gross vs salary. Different upload templates fill different sets. Your payslip renderer must coalesce rather than trust one column.

Quirks to expect

GET /api/employee/get runs a blanket UPDATE on every call, backfilling null units — a list read has write side effects. salary_slips.emp_code is an integer while users.emp_code is a string(100), so codes with letters won't join. Ichapur belongs to both companies. The RBAC model is permissive by default. Several deletes are GET. And GET /api/gautampithadiya is a leftover debug route that should be removed.

Before you start

  • Get a staging copy of the API — you will be creating and deleting test employees.
  • Confirm the JWT TTL, and decide now whether you need a refresh endpoint.
  • Decide the payslip PDF strategy early; it shapes phase 5.
  • Ask for the three security fixes above as backend work in parallel with phase 1.
  • Check whether CORS on niss.pro needs changing — native clients don't send Origin the same way browsers do, and the current config is permissive but worth verifying.
