Five findings matter. In order of how much damage they can do:

1. **The `permission:` middleware is decorative.** Not one `admin.*` or `hr.*`
   permission exists in the 96-row catalogue, so the new engine denies every
   one of them, shadow mode catches the deny, and the legacy check returns
   `'admin' => true` — unconditional allow. Any legacy admin can publish
   authorization policies, assign roles and issue emergency grants.
2. **The PHP authorization code cannot write to its own tables.** Production's
   authorization schema is a different implementation from the one the PHP
   models and controllers were written against; eighteen referenced columns do
   not exist. Thirty-six routes are registered on them.
3. **`php artisan migrate` is blocked.** The authorization migration is
   unrecorded but its tables exist, so the run aborts on the first
   `Schema::create` — stranding the thirteen HR migrations behind it. The HR
   UI, API client, routes and controllers are all deployed against tables that
   do not exist.
4. **Aadhaar numbers are in S3 object keys.** 37 of 38 document versions have a
   twelve-digit first path segment; 14 are confirmed equal to a real
   `users.aadhar_card_no`.
5. **Nothing scans uploads.** All 38 versions are `scan_status = NOT_SCANNED`.

Repairs written, none applied — see §9.

## 3. Authorization report

### 3.1 Two implementations of the same eleven tables

`prisma/sql/0001` built what production has. The PHP migration, models,
services and controllers describe something different. **49 structural
differences**, of which the ones that break code are eighteen missing columns:

| Table | Missing | Written by |
|---|---|---|
| `permissions` | `level` | `PermissionController::store`, `::update` |
| `authorization_role_assignments` | `assignment_source`, `assignment_reason` | `EnterpriseRoleController::assign`, `AccessRequestController::approve`/`::revoke` |
| `authorization_role_inheritances` | `max_depth`, `inherit_sensitive` | `EnterpriseRoleController::inherit` |
| `authorization_policies` | `audit_required`, `approved_at` | model `$fillable`; `PolicyController::publish` |
| `authorization_policy_versions` | `approved_at`, `effective_at`, `deployment_status`, **`updated_at`** | `PolicyController::store`/`::publish`/`::rollback` |
| `authorization_access_requests` | `permission_code`, `decision_reason` | `AccessRequestController` (all five actions) |
| `authorization_sod_rules` | `conflicting_role_codes`, `conflicting_permission_codes`, `enforcement` | `SeparationOfDuties::conflicts` |
| `authorization_decision_logs` | **`updated_at`** | `AuthorizationEngine::finish` |
| `authorization_feature_flags` | `configuration` | model `$fillable` + array cast |

The two `updated_at` absences are the sharpest: Eloquent puts both timestamps in
every INSERT, so those tables cannot be written to at all. The decision log
survives only because `AuthorizationEngine::finish` wraps the write in a
`try {} catch {}` — **the authorization audit trail is silently discarding every
record**, which is exactly the failure mode an audit trail must not have.

`SeparationOfDuties::conflicts` is called on the two write paths that matter
most, role assignment and access-request approval. Both raise 42703 today.

Differences that are *not* problems, and are deliberately left alone:
production carries extra columns from 0001 (a superset); several columns are
nullable where PHP declares NOT NULL (production is the more permissive side, so
PHP's writes still succeed); six indexes exist under different names with the
same columns.

### 3.2 Empty tables, and why that is dangerous

All 15 `authorization_*` tables have 0 rows, including
`authorization_feature_flags`.

`RequirePermission::schemaReady()` returns **true** in production — every table
and column it probes is present. So the full engine runs. With no role
assignments and no policies, it denies. The request survives only because:

```php
$shadow = $this->flags->enabled('authorization_shadow_mode', $actor->company_code, true);
if (!($shadow && ($decision->legacyDecision['allowed'] ?? false))) { return 403; }
```

The flags table is empty, so `enabled()` returns the `true` **baked into the
call site**. Production's entire authorization behaviour rests on a default
argument rather than on anything visible in the database. **One row setting
`authorization_shadow_mode = false` denies every permission-checked request in
the application.** Nothing surfaces that this is the state.

### 3.3 The finding that matters most

`legacyDecision` (AuthorizationEngine.php:354):

```php
if ((int) $actor->role === 0) return ['allowed' => true, ...];         // super admin
if (str_starts_with($permissionCode, 'admin.authorization.')) return false;
$allowed = match ($this->legacyRole($actor)) {
    'admin'    => true,                                                // ← everything
    'agent'    => Str::startsWith($code, ['recruitment.', 'hr.appointment.', 'document.']),
    'employee' => Str::startsWith($code, ['self.', 'payroll.payslip.read', 'hr.profile.']),
    default    => false,
};
```

The permission catalogue has 96 rows across 14 areas — `platform`, `company`,
`dashboard`, `workforce`, `employees`, `appointments` and so on. It contains
**zero `admin.*` codes and zero `hr.*` codes**.

So for all 36 authorization routes and all HR routes: the engine finds no
permission, denies; shadow mode is on; `legacyDecision` is consulted; the actor
is a legacy admin; `'admin' => true`. **Allow.**

`admin.authorization.*` is explicitly blocked — but not one of the 36 routes
uses that prefix. They are `admin.role.*`, `admin.policy.*`, `admin.permission.*`,
`admin.access_request.*`, `admin.delegation.manage`, `admin.emergency_access.approve`.
Every one falls through to the unconditional allow.

`permission:admin.role.delete` and `permission:admin.policy.publish` read like
fine-grained gates. Today they are equivalent to `role:admin`. The mechanism
that would make them real — policies, role assignments, a permission catalogue
covering `admin.*` — is deployed and empty.

Fixing this is not schema repair and is not attempted here. It needs the
`admin.*`/`hr.*` permission codes seeded and assigned, which is a decision about
who should hold what.

## 5. Storage report

38 documents, 38 versions, one bucket `niss-568521409387-eu-north-1-an`
(eu-north-1). All `ACTIVE`. All 38 have `s3_object_key`, `s3_version_id`,
`checksum`, `etag` and `encryption_type` populated.

The brief asks about `s3_bucket`, `s3_region` and `storage_provider`. **Those
columns do not exist.** The bucket is `bucket_name`; region is not stored
separately (it is encoded in the bucket name); there is no provider column —
provider is `config/documents.php` + `DOCUMENT_STORAGE_PROVIDER`, which you
confirmed is `s3`.

**Reads are safe against a naming change.** `s3_object_key` is `NOT NULL` and
begins with `folder_path` in all 38 rows, but both are *stored per version*, not
recomputed. So legacy objects resolve from the database regardless of what
scheme new writes use. The two schemes can coexist — this is what §9's Aadhaar
change depends on, and it is now verified rather than assumed.

Layout is `<segment>/<user_id>/<TYPE>`:

| Check | Result |
|---|---|
| First segment is 12 digits | 37 / 38 |
| First segment equals a real `users.aadhar_card_no` | **14 confirmed** |
| `documents.user_id` NULL | **28 / 38** |
| `scan_status = NOT_SCANNED` | **38 / 38** |
| `document_audit_logs` | 2,528 rows |

And the state of the Aadhaar columns across 339 users:

| `aadhar_card_no` (raw) | `encrypted_aadhaar_number` | `aadhaar_secure_reference` |
|---|---|---|
| 334 | **0** | **0** |

The encryption and HMAC-reference columns exist and are entirely unpopulated.
Aadhaar numbers are stored in plaintext and embedded in object keys. The Node
side can compute the reference from the raw number at write time, so the
write-HMAC / read-legacy scheme needs no backfill to start.

28 of 38 documents having a NULL `user_id` also means ownership is carried only
by the path — which is the other reason the path contains an Aadhaar number.

## 9. Repair scripts

Three, written and reviewed. **None has been applied** — the classifier declined
the DDL run, and I did not route around it.

### `salary-slip-node/prisma/sql/0003_php_authz_parity.up.sql`

Adds the eighteen missing columns and six genuinely-absent indexes. Additive
only: nothing dropped, retyped, or made stricter; no row modified. All eleven
tables are empty, so the NOT NULL DEFAULTs are metadata-only;
`permissions.level` lands on 96 rows with the same `'ACTION'` default the PHP
migration declares. Idempotent (`ADD COLUMN IF NOT EXISTS` throughout).

Reversible: `0003_php_authz_parity.down.sql`.

### `salary-slip-node/prisma/sql/0004_authorization_feature_flag_defaults.up.sql`

Seeds the seven flags, values copied exactly from the PHP migration's own seed
loop. **Behaviour-preserving**: shadow mode was already effectively `true` via
the call-site default, so this changes nothing except making it visible.
`authorization_engine_v2` and the other five are read only by
`GET /authorization/flags`, with a `false` default — seeding them `true` makes
the administration UI show the platform as available. Nothing else consumes
them.

Idempotent: an existing row for a key is left untouched, so it can never
overwrite an operator's deliberate change.

Reversible: `0004_...down.sql`.

> The brief's example defaults (`authorization_enforcement`, `audit_enabled`)
> are not keys this codebase reads. Seeding them would create config that looks
> load-bearing and is not. The seven real keys are used instead.

Apply both with:

```
cd salary-slip-node
npx tsx scripts/authz-migrate.ts up --dry-run   # verified: would apply 0003, 0004
npx tsx scripts/authz-migrate.ts up
```

### `docs/repair/record-authz-migration.sql`

Records the authorization migration in Laravel's `migrations` table, which is
what unblocks the thirteen HR migrations. Two guards: it aborts if 0003 has not
been applied, and aborts if the tables are somehow absent. Rollback is one
`DELETE`, in the file.

**Run this only after 0003 and 0004, and only once you have confirmed the
authorization migration file is the same in whichever codebase deploys this
database.** §2.2 shows eleven applied migrations whose files are not in this
repository. Every other repair here is additive and self-evident; this one makes
Laravel *skip* a migration forever, and if the deployed variant differs, the
skip is silent and permanent. That asymmetry is why it is not automated.

### Not repaired, deliberately

- The `admin.*`/`hr.*` permission gap (§3.3) — needs a decision about who holds
  what, not a schema change.
- `AuthorizationPolicy.description` is `VARCHAR(500)` while `PolicyController`
  validates `max:1000`. A 501–1000 character description passes validation then
  fails at the database. One-line ALTER, but it is a behaviour change rather
  than drift repair.
- Nullability and index-name differences (§3.1) — benign, and tightening them
  adds risk without adding compatibility.

## 13. Rollback plan

| Step | Undo |
|---|---|
| 0003 | `npx tsx scripts/authz-migrate.ts down 0003 --confirm` |
| 0004 | `npx tsx scripts/authz-migrate.ts down 0004 --confirm` |
| migrations row | `DELETE FROM migrations WHERE migration = '2026_08_03_000001_create_enterprise_authorization_platform';` |
| Prisma | `git checkout prisma/schema.prisma && npx prisma generate` |

Order matters: undo the `migrations` row before 0003, or Laravel will consider
the migration applied while its columns are gone.

**Do not use `php artisan migrate:rollback` on this batch.** The migration's
`down()` calls `dropIndex('roles_tenant_status_index')`, and production has that
index as `roles_tenant_status_idx`. The rollback fails partway — after the
eleven tables have already been dropped. Use the table above.

`pg_dump` is not installed on this host (the PostgreSQL directory ships `lib`
and `share` only). The safety net is the `_pre_authz_*` snapshot tables, which
live in the same database they protect and are therefore not a substitute for a
real dump. **Take one before applying anything.**
