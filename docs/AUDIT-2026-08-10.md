# HRMS Full Audit Report

**Audit date:** 10 August 2026  
**Repository:** `HRMS oldd`  
**Audited state:** current working tree on `main`, including uncommitted user changes  
**Overall decision:** **NO-GO for production release**

## 1. Executive summary

The active HRMS has substantial functionality, a meaningful automated-test estate, and several good security controls. It is not currently release-ready. The most urgent risks are:

1. The mobile application sends credentials, bearer tokens, and HR data to a hard-coded HTTP endpoint. Android explicitly permits cleartext traffic to that host, the session is stored in AsyncStorage, and application backup is enabled.
2. Aadhaar remains in a plaintext database column for most affected users. Full Aadhaar is also returned on ordinary record-access paths, including bulk lists, and those disclosures use best-effort audit logging.
3. Uploaded document versions are not malware-scanned or quarantined before use.
4. All three primary release gates are currently red: frontend lint, frontend tests, and the full Laravel test suite.
5. The new authorization system remains in shadow mode for most permissions, while legacy integer roles still influence access. The permission catalog and actual enforcement have significant drift.

The production database is reachable and active, with the HR module tables present. This is not a finding of total platform failure. It is a finding that the current release process cannot demonstrate a safe, reproducible build and that sensitive-data controls need remediation before wider production or mobile rollout.

## 2. Scope and method

The audit covered:

- Repository and application architecture
- Active Laravel, React, Fastify/Prisma, and Expo applications
- Dormant HRFlow and Enterprise RBAC applications where they still affect repository risk
- Authentication, authorization, Aadhaar handling, document access, uploads, audit logging, CORS, and security headers
- Production database structure and selected control counts through read-only probes
- Unit, feature, integration, build, type-check, lint, dependency, and Expo diagnostics
- CI workflows, deployment documentation, generated artifacts, and secret-handling practices
- Source-level accessibility and frontend performance indicators

This was not an external penetration test. The audit did not modify AWS resources, inspect the live S3 bucket or mail provider, intercept network traffic, test real OTP delivery, run destructive database checks, or perform browser-based cross-device visual testing.

### 4.3 Laravel test isolation failure

The full Laravel suite is not order-independent. `tests/Feature/HrModuleSchemaGateTest.php:176` calls `migrate:fresh` from `tearDown()` while `RefreshDatabase` transaction handling is active. This is a test-harness defect, not evidence that all 235 corresponding product behaviors are broken. It is nevertheless a release blocker because the suite cannot establish regression safety.

## 6. Detailed findings

### C-01 — Mobile credentials and HR data use cleartext HTTP

**Evidence**

- `hrms-mobile-app/src/services/api.js:3` and `pushNotifications.js:8` hard-code `http://192.168.1.53:8000/api`.
- `android/app/src/main/res/xml/network_security_config.xml:13` permits cleartext for the target host.
- `src/services/api.js:228` persists the session in AsyncStorage.
- `android/app/src/main/AndroidManifest.xml:35` enables application backup.

**Impact**

Anyone able to observe or manipulate the same network can steal credentials or bearer tokens and read or alter HR data. AsyncStorage and Android backup further widen token-extraction risk on a compromised or backed-up device.

**Required action**

Block release of the mobile client until all API traffic uses validated HTTPS. Move bearer/session secrets to platform-backed secure storage, make the API origin environment-specific, remove the production cleartext exception, and disable backup or explicitly exclude secrets. Rotate credentials/tokens that may have been used over untrusted networks.

### C-02 — Release evidence is not reproducible

Frontend lint and tests fail, and the full backend suite corrupts its own shared schema. A release from this tree cannot be tied to a green, repeatable set of controls.

**Required action**

Fix the two frontend test selectors, reduce lint errors below the gate, and redesign schema-mutating Laravel tests to use isolated databases or explicit schema restoration outside active transactions. Require the resulting green workflow before deployment.

### H-01 — Aadhaar dual-write still retains plaintext

`salary-slip-bac/app/Models/User.php:172-180` explicitly retains `aadhar_card_no` plaintext while also preparing encrypted fields. The production probe found 337 plaintext rows and only 10 encrypted rows.

**Impact**

A database read, backup leak, support export, or SQL injection would expose full identity numbers. Encryption added alongside plaintext does not reduce the original exposure.

**Required action**

Backfill and verify every valid Aadhaar value, change every reader to prefer the encrypted representation, add last-four/reference fields for normal workflows, then null and drop the plaintext column. Separate encryption keys from database backups and document rotation/recovery.

### H-02 — Full Aadhaar follows ordinary record access, including lists

`app/Support/AadhaarAccess.php` deliberately uses record access rather than a sensitive-data permission. `AadhaarDisclosure::fullFor()` reads the raw plaintext field and list endpoints can return complete numbers. The production trail recorded 3,370 full-number disclosures, including employee, candidate, trial-form, appointment, and employee-detail lists.

**Impact**

Users who legitimately need to find or open an employee can receive substantially more identity data than their task requires. Bulk-list disclosure increases breach impact and makes scraping easier.

**Required action**

Mask Aadhaar by default in all list and detail responses. Require a narrowly assigned, purpose-bound reveal permission for the full value, with reauthentication or a short-lived reveal token where practical. Prohibit full Aadhaar in bulk endpoints and exports unless a separately approved workflow exists.

### H-03 — Sensitive disclosure logging fails open

`app/Support/AadhaarDisclosure.php:38-55` and `:89-105` use `DocumentAudit::recordSafely()`, deliberately allowing the disclosure if the audit insert fails. Bulk logs record only a count and context, not target IDs. The authorization engine also catches logging exceptions and continues (`AuthorizationEngine.php:510`). Production has 3,392 document audit rows but only 113 general audit rows.

**Impact**

The most sensitive read paths can operate without a durable, attributable record. A logging outage can silently remove forensic evidence while access continues.

**Required action**

For full Aadhaar and confidential export paths, enqueue a durable audit event transactionally or fail closed. Add target identifiers or a signed manifest for bulk access, alert on audit-pipeline failure, and reconcile application events to immutable centralized logs.

### H-04 — Documents are usable without malware clearance or quarantine

All 11 document versions observed in production were `NOT_SCANNED`; none were malware-cleared, and the schema has no quarantine indicator.

**Impact**

An uploaded malicious document can be stored and later downloaded by HR or administrative users, turning the HRMS into a delivery channel.

**Required action**

Upload to a private quarantine prefix, validate type by content and extension, scan asynchronously, and permit download only after a clean verdict. Record scanner version/result, size, hash, and timestamps. Treat timeouts and scanner errors as non-downloadable states.

### H-05 — Authorization is mostly shadowed and catalog coverage is incomplete

`config/authorization.php:7` defaults to `shadow`. Only security-administration prefixes are always enforced. The permission report found:

- 309 catalog codes
- 121 codes used by enforcement checks
- 115 of 121 covered (95.04%)
- 6 missing enforced codes, all in `hr.*`
- 194 catalog codes not referenced by enforcement
- 120 production permissions assigned to no role

When a new authorization decision denies in shadow mode, legacy authorization can still allow the request. `users.role` remains an effective authority channel.

**Impact**

Administrators can believe RBAC configuration is enforced when many decisions are advisory or are still decided by legacy role logic.

**Required action**

Resolve the six missing codes, classify or retire unused catalog entries, map every required permission to roles, compare shadow decisions with legacy outcomes, and then roll out enforcement by module with rollback metrics. Remove the legacy integer role only after parity is demonstrated.

### H-07 — Production authorization schema has no single owner

Laravel migrations, Node migrations, live tables, and the verification script disagree. The Node migration ledger is absent, while the live schema contains only part of the Node governance model.

**Impact**

Future migrations can duplicate, omit, or destroy authorization data. Verification output is not presently reliable enough to be a hard release decision.

**Required action**

Declare one migration owner, reconcile the live schema to a canonical manifest, repair the expected-table list, baseline the live database without replaying destructive migrations, and require drift-free checks thereafter.

### H-08 — Tenant/company build selection depends on the Git branch

The active frontend Vite configuration derives company theme, API target, and output directory from the current Git branch. Detached HEAD builds, branch renames, or incorrectly based release branches can silently produce the wrong tenant artifact.

**Required action**

Make tenant an explicit validated build parameter, embed tenant/build identity in the artifact, fail on missing or unknown values, and generate each tenant artifact in CI from the same immutable source revision.

### M-01 — CSP and non-production CORS need hardening

Laravel's CSP contains both `'unsafe-inline'` and `'unsafe-eval'` (`SecurityHeaders.php:17-18`). Non-production CORS can use a wildcard origin. Bearer-token APIs do not require credentialed CORS, but a reachable development/LAN deployment should still restrict origins. Confirm that the same headers are applied by the actual static frontend host; Laravel middleware alone does not protect files served directly by a proxy or CDN.

### M-02 — Frontend bundles are large

The build succeeds but produces major chunks including AG Grid at approximately 1.12 MB, ExcelJS at 937 KB, the main bundle at 455 KB, Add Employee at 370 KB, and chart code at 344 KB. The PWA precaches 142 entries totaling about 5.63 MiB.

Use route-level lazy loading, load spreadsheet/grid functionality only when requested, review PWA precache selection, and enforce bundle budgets. The dormant HRFlow client also produces a 778 KB bundle.

### M-03 — Active frontend maintainability is deteriorating

The active frontend has about 72,000 source lines and several very large modules: `Appointments.jsx` is over 100 KB, `api.js` about 86 KB, and multiple pages/components are 55–81 KB. The 131 lint errors include unused variables, state changes inside effects, dependency-array issues, and React Fast Refresh violations.

Split API clients by domain, separate data orchestration from presentation, and reduce page components behind tested hooks and smaller feature modules.

### M-04 — Generated and built artifacts are tracked

The repository tracks 218 files under frontend `main/` output and 27 generated Prisma files totaling about 42.73 MB, including a native query engine and very large type output. The working tree currently contains 263 changed-status entries, mostly because generated frontend assets were already dirty and were refreshed by the audit build.

Generated artifacts should be created in CI and published as release artifacts, not treated as source. If checked-in output is an intentional deployment mechanism, update it only through a deterministic, reviewed release job.

### M-05 — Mobile project configuration is inconsistent

Expo Doctor passed 11 of 17 checks. Failures include `.expo` ignore handling, an invalid `android.navigationBarColor` configuration, direct `expo-modules-core`, Metro 0.87 packages where Expo expects approximately 0.80.8, native/config synchronization risk, and a declared AsyncStorage dependency that Doctor could not validate. There are no mobile lint or test scripts.

Align packages with the Expo SDK, choose either managed prebuild ownership or explicit native ownership, then add lint, unit, Android build, and dependency checks to CI.

### M-06 — Audit and database observability are limited

PostgreSQL reported `log_statement=none` and no duration threshold. Database-level DDL visibility is therefore weak. Application logging should not include secret or Aadhaar values, but schema changes, privilege changes, and security-control failures need durable events and alerts.

### M-07 — Repository documentation and component status are ambiguous

The root documentation foregrounds a stack whose server no longer compiles. There is no authoritative statement of which applications are deployable, migration-only, dormant, or archived.

Create a root architecture and release map with owners, supported commands, database ownership, deployment targets, environment variables, and decommission status.

### M-08 — End-to-end and visual release checks are absent

No Playwright or Cypress files were found. Source-level tests cover many components, including some accessibility behaviors, but there is no automated proof of complete authentication, employee, appointment, document, payroll, or role-management journeys in a real browser. No Lighthouse, keyboard-only, screen-reader, or cross-device visual audit was run.

Add a small deterministic E2E suite for the highest-risk workflows and an accessibility check such as axe. Keep sensitive test fixtures synthetic.

## 7. Positive controls observed

- Composer reports no known advisories or abandoned packages.
- The Fastify/Prisma backend passes build, type-check, and 647 tests.
- Frontend PWA runtime caching is limited to static assets/fonts; API responses are not configured for offline caching.
- Confidential export paths use a separate permission and one-time token and are designed to fail closed on audit failure.
- Security headers include HSTS in production, `nosniff`, frame denial, and a restrictive referrer policy.
- No tracked PEM/private-key file or committed runtime `.env` file was found.
- Root `.gitignore` covers PEM files, environment files, archives, and database dumps.
- The current uncommitted OTP change gates development fallback behind explicit `OTP_DEV_FALLBACK=true` and avoids logging the OTP.
- The permission catalog has no duplicate codes, and enforced-code coverage is measurable.
- No clear user-input SQL injection path was identified in the inspected application queries; raw queries observed were constant or parameterized.

These controls reduce risk but do not offset the no-go findings.

## 8. Secrets and deployment hygiene

`HRM.pem` exists in the project root but is ignored and untracked. It was not read during this audit. Keeping a private key inside the working project tree makes accidental packaging, backup, or local compromise more likely; move it to a managed secret/key store with minimum filesystem permissions and rotate it if provenance is uncertain.

Deployment archives in the workspace include `.env.production` files. Vite variables are public build-time configuration by design, but archives should be inventoried, checksummed, access-controlled, and removed when superseded. CI's current secret check mainly checks names/history; add content scanning with an allowlisted secret scanner.

The OTP fallback hardening and frontend privilege-normalization changes are currently uncommitted. Confirm that they are reviewed, committed, deployed, and verified before relying on them as mitigations.

### Within 24 hours

1. Block mobile distribution and require HTTPS, secure token storage, and backup restrictions.
2. Mask full Aadhaar in all list responses; temporarily restrict reveal capability to a minimal audited administrator group.
3. Disable download of unscanned uploads or place all new uploads in quarantine.

## 10. Release acceptance criteria

A release should not be approved until all of the following are true:

- Mobile has no production cleartext path and secrets use platform secure storage.
- Full Aadhaar is masked by default, encrypted at rest, and not present in bulk responses.
- Sensitive disclosures and exports have durable, monitored audit records.
- Documents cannot be downloaded before a clean malware verdict.
- Frontend lint and tests, Laravel tests, Node tests/type-check/build, mobile Doctor/build, and dependency policy all pass in CI.
- Authorization schema drift is zero against a corrected canonical manifest.
- The six missing enforced permission codes are resolved and shadow/enforced scope is documented.
- The tenant and source revision are embedded and verified in every artifact.
- A clean checkout can reproduce the released artifacts without relying on uncommitted or locally generated state.

## 11. Audit limitations and workspace note

The production checks were read-only and sampled application control state; they were not a complete data-classification exercise. AWS IAM, S3 bucket policies and current object keys, TLS termination, firewall rules, host patching, backups, disaster recovery, email/SMS providers, and third-party contracts require separate infrastructure evidence.

The repository was substantially dirty before the audit. Running the requested production frontend build refreshed the already tracked/generated `salary-slip-front/salary-slip-front/main/` assets, increasing the visible Git diff. No application source was intentionally modified by the audit; this report is the intentional audit artifact. Existing changes were not reverted because they belong to the user and could not safely be separated from prior generated-output changes.

---

**Disposition:** Remediate Critical and High findings, restore green reproducible release gates, and perform a focused verification audit before production approval.
